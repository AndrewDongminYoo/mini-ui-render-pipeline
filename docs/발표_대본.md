## 1. 도입 (2분)

### 자기소개 (30초)

안녕하세요. 이번 과제전형에 참여한 유동민입니다. 저는 Flutter를 활용한 모바일 앱 개발 경험을 바탕으로 이번 과제를 수행했습니다. 오늘은 제가 구현한 **Mini UI Render Pipeline** 프로젝트에 대해 설명드리겠습니다.

### 문제 정의 (30초)

이 과제의 핵심은 **"UI 트리 구조와 상태 변경 이벤트를 처리하여, 어떤 노드를 다시 계산해야 하는지 결정하는 렌더링 파이프라인"**을 구현하는 것입니다.

**입력**: 트리 구조 + 이벤트 리스트
**출력**: 구조 변경 노드 + 레이아웃 재계산 노드 + 페인트 순서

핵심은 **Dirty Flag 기반 증분 업데이트**와 **결정성 보장**입니다.

### 프로젝트 개요 (60초)

제가 구현한 시스템의 특징은 다음과 같습니다:

1. **6가지 이벤트 타입** 지원 (setSize, setPosition, setState, addChild, removeChild, moveChild)
2. **4가지 노드 타입** 구현 (Box, Row, Column, Stack)
3. **217개 테스트**로 검증된 구현
4. **결정성 보장** - 동일 입력은 항상 동일 출력

시스템 구조는 **Parser → NodeTree → Engine → Scheduler → Calculator → Renderer** 순서로 데이터가 흐릅니다.

## 2. 핵심 설계 결정 5가지 (10분)

### 2.1 Two-Tier Dirty Flags (2분)

**결정**: `structureDirty`와 `layoutDirty` 두 가지 플래그를 분리했습니다.

```dart
abstract class Node {
  bool structureDirty = false;  // 트리 구조 변경
  bool layoutDirty = false;     // 레이아웃 재계산 필요
}
```

**왜 분리했나?**

1. **영향 범위가 다릅니다**
   - 구조 변경 (addChild): 트리 위상 자체가 바뀜
   - 속성 변경 (setSize): 크기/위치만 바뀜

2. **출력 형식 요구사항**
   - `recomputeStructure`와 `recomputeLayout`을 별도 리스트로 출력
   - 두 플래그가 있어야 정확히 구분 가능

3. **최적화 효과**
   - 속성 변경 시 구조 검증 과정 건너뛰기 가능
   - 불필요한 재계산 방지

**반례**: 1-tier로 통합하면?

- addChild 후 모든 노드가 "다시 계산 필요"로 표시
- 실제로는 구조만 바뀌고 레이아웃은 변경 없을 수 있는데 구분 불가

---

### 2.2 No-op Detection (2분)

**결정**: 이벤트 처리 전 변경 여부를 먼저 확인합니다.

```dart
void _processSetSize(SetSizeEvent event) {
  final node = tree.findNode(event.targetId);

  // No-op detection
  if (node.size == event.newSize) {
    return; // 변경 없음, Dirty 전파 건너뛰기
  }

  node.size = event.newSize;
  _markDirty(node);
}
```

**왜 필요한가?**

1. **불필요한 전파 차단**
   - 현재 크기가 100×50인데 100×50으로 setSize하면 아무 일도 안 해야 함
   - No-op detection 없으면 부모/형제까지 Dirty 표시됨

2. **출력 정확성**
   - 실제 변경 없는 이벤트는 `recomputeLayout`이 비어있어야 함
   - 사용자 입장에서도 "왜 재계산?"이라는 의문이 생기지 않음

3. **성능 최적화**
   - 실제 프로덕션 환경에서 no-op 이벤트는 빈번함
   - 예: 애니메이션 프레임마다 동일 값 설정 시도

**검증 방법**: 테스트에서 동일 크기 설정 시 `recomputeLayout`이 빈 배열인지 확인

---

### 2.3 recomputeLayout 순서 규칙 (2분)

**결정**: **직접 타겟 → 부모들 → 형제들** 순서로 출력합니다.

```diagram
이벤트 타겟 (A) → 부모 방향 (R) → 형제 (B)
```

**예시로 설명**:

```diagram
트리 구조:
R (Row, 80×20)
├── A (Box, 50×20)  ← setSize 타겟
└── B (Box, 30×20)

Event: setSize(A, {w:60, h:20})

Dirty 전파:
1. A.layoutDirty = true    (직접 변경)
2. R.layoutDirty = true    (부모: Row 너비 재계산 필요)
3. B.layoutDirty = true    (형제: 위치 재배치 필요)

결과: recomputeLayout = ["A", "R", "B"]
       ↑직접  ↑부모  ↑형제
```

**왜 이 순서인가?**

1. **인과관계 명확성**
   - A가 변경 → R이 영향받음 → B가 영향받음
   - 원인(타겟) → 1차 영향(부모) → 2차 영향(형제)

2. **디버깅 편의성**
   - 출력 리스트 첫 번째 요소가 이벤트 타겟
   - "왜 이 노드가 재계산되나?" 추적 용이

3. **Flutter 렌더링과의 유사성**
   - Flutter도 변경 → 부모 통지 → 형제 레이아웃 순서

**반례**: 랜덤 순서면?

- ["B", "A", "R"] 같은 결과는 기술적으로 맞지만
- 사용자가 "왜 B가 먼저?"라고 혼란 겪음
- 결정성도 깨질 수 있음 (Set 사용 시)

### 2.4 Cascading Layout Updates (2분)

**결정**: **Fixed-point iteration**으로 연쇄 레이아웃 업데이트를 처리합니다.

```dart
void _recalculateLayoutsCascading(NodeTree tree, Scheduler scheduler) {
  const maxIterations = 10;
  int iteration = 0;

  while (iteration < maxIterations) {
    final updated = scheduler.recalculateDirtyLayouts();
    if (updated.isEmpty) break;  // 수렴

    // 부모 노드들을 다음 iteration을 위해 Dirty 표시
    for (final nodeId in updated) {
      final node = tree.findNode(nodeId);
      node?.parent?.markLayoutDirty();
    }

    iteration++;
  }
}
```

**왜 필요한가?**

**시나리오**: 깊은 중첩 구조에서 리프 노드 크기 변경

```
GrandParent (Column)
└── Parent (Row)
    └── Child (Box)  ← setSize

1차 계산: Child 크기 변경 → Parent.layoutDirty
2차 계산: Parent 크기 변경 → GrandParent.layoutDirty
3차 계산: GrandParent 크기 확정 → 수렴
```

**수렴 보장**:

1. **상향 전파만 허용** (자식 → 부모)
2. **트리 구조 고정** (이벤트 처리 중 트리 변경 없음)
3. **maxIterations = 10** (트리 깊이 < 10이면 항상 수렴)

**검증**: 테스트에서 4단계 중첩 구조로 수렴 확인

### 2.5 Pre-order DFS for Paint Order (2분)

**결정**: **부모 → 자식** 순서로 paintOrder를 생성합니다.

```diagram
트리:
R
├── A
│   ├── A1
│   └── A2
└── B

Paint Order: [R, A, A1, A2, B]
             ↑부모 먼저, 자식은 나중에
```

**왜 Pre-order DFS인가?**

1. **렌더링 시스템의 일반 원칙**
   - 부모 레이어가 먼저 그려져야 함
   - 자식은 부모 위에 덧그려짐
   - z-index 순서: 부모 < 자식

2. **CSS/Flutter와의 일관성**
   - CSS: stacking context에서 부모 먼저
   - Flutter: CustomPainter에서 부모 canvas 먼저

3. **코드 단순성**
   - Pre-order DFS는 재귀로 간단히 구현
   - 다른 순회 방식은 복잡도 증가

**대안 (Post-order)은?**

- [A1, A2, A, B, R] 순서
- "자식 먼저, 부모 나중" → 배경이 자식을 덮어버림
- 실제 렌더링 시스템과 맞지 않음
