# APR 실무면접 — 과제 발표 스크립트 (말하기 버전, 12분)

## 0) 오프닝 (0:00–0:20)

안녕하세요. 과제 전형에 참여한 **유동민**입니다.
오늘은 제가 구현한 **Mini UI Render Pipeline**을 통해, **복잡한 규칙을 스펙으로 고정하고 테스트로 검증하는 방식**을 중심으로 설명드리겠습니다.

---

## 1) 문제 정의 & 한 줄 요약 (0:20–1:30)

### 1.1 문제 정의 (0:20–0:50)

이 과제는 간단히 말하면,
**UI 트리와 상태 변경 이벤트를 입력으로 받아서, “어느 노드를 다시 계산해야 하는지”를 결정하는 시스템**입니다.

- **입력**: 트리 구조 + 이벤트 리스트
- **출력**:
  1. 구조 변경 노드 목록 `recomputeStructure`
  2. 레이아웃 재계산 노드 목록 `recomputeLayout`
  3. 렌더 순서 `paintOrder`

### 1.2 한 줄 요약 (0:50–1:10)

제가 잡은 핵심은 한 줄로,
**“Dirty Flag 기반의 증분 업데이트를, 결정성 있게 출력한다”** 입니다.

### 1.3 구현 범위 (1:10–1:30)

- 이벤트 6종: setSize, setPosition, setState, addChild, removeChild, moveChild
- 노드 4종: Box, Row, Column, Stack
- 그리고 결과를 **테스트로 잠가서**, 총 **217개 테스트**로 검증했습니다.

---

## 2) 시스템 흐름 (1:30–2:20)

전체 구조는 이렇게 단순하게 가져갔습니다.

**Parser → NodeTree → Engine → Scheduler → Calculator → Renderer**

- Parser가 JSON 입력을 모델로 바꾸고
- Engine이 이벤트를 적용하면서 dirty를 표시하고
- Scheduler가 “어떤 순서로 어떤 노드를 재계산할지”를 정리하고
- Calculator가 실제 레이아웃 값을 계산하고
- Renderer가 결과 리스트를 출력합니다.

여기서 중요한 건, “계산을 많이 하는 것”이 아니라
**계산해야 하는 대상을 정확히, 일관된 순서로, 재현 가능하게 뽑는 것**입니다.

---

## 3) 핵심 설계 결정 5가지 (2:20–9:50)

### 3.1 Two-tier dirty flags: structure vs layout (2:20–3:40)

첫 번째 결정은 **dirty flag를 두 종류로 분리**한 겁니다.

- `structureDirty`: 트리 구조가 바뀐 경우
- `layoutDirty`: 크기/위치/상태 때문에 레이아웃 계산이 필요한 경우

**왜 굳이 나눴냐**면, 이유는 2개입니다.

1. **정확성**: 구조 변경과 속성 변경은 영향 범위가 다릅니다.
   - addChild는 트리 위상이 바뀌고
   - setSize는 크기만 바뀝니다.

2. **출력 스펙**: 과제 출력이 `recomputeStructure` / `recomputeLayout`을 분리해서 요구합니다.
   1-tier로 합치면 나중에 다시 “이건 구조였나 레이아웃이었나”를 **역추론**해야 하고,
   그 순간 로직이 복잡해지고 테스트 표면이 늘어납니다.

즉, 이 분리는 “최적화” 이전에
**스펙을 코드 구조로 그대로 옮긴 것**에 가깝습니다.

---

### 3.2 No-op detection: 변경 없으면 0 비용 (3:40–4:50)

두 번째 결정은 **no-op detection**입니다.

예를 들어 setSize 이벤트가 왔는데,
기존 값과 새 값이 같다면 **아무 것도 하지 않습니다**.

이게 중요한 이유는 한 문장으로,
**“변경이 없는데 dirty를 전파하면 출력이 오염된다”** 입니다.

- 변경이 없으면 `recomputeLayout`은 비어야 하고
- 부모/형제까지 dirty가 전파되면 사용자는 “왜 재계산?”이 됩니다.

그리고 운영 관점에서도 no-op은 자주 나옵니다.
예를 들어 UI 프레임이나 외부 입력에서 동일 값이 반복되는 경우가 있습니다.

결론적으로, no-op detection은
**정확성과 비용을 동시에 지키는 안전장치**입니다.

---

### 3.3 recomputeLayout 순서 규칙: 타겟 → 부모 → 형제 (4:50–6:20)

세 번째는 `recomputeLayout`의 **출력 순서 규칙**입니다.

저는 **타겟 → 부모들 → 형제들** 순서로 고정했습니다.

왜냐면 이 과제는 “계산 결과”보다,
**결과를 사람이 해석 가능한 순서로 제공하는 것**이 중요하기 때문입니다.

간단한 예시로, Row 아래에 A, B가 있고 A의 width가 커지면:

- A는 직접 변경
- Row는 전체 폭을 다시 계산
- B는 위치가 밀려서 재배치

그래서 결과를 `["A", "R", "B"]`로 고정합니다.

여기서 제가 강조하고 싶은 포인트는:
이 순서는 “유일한 정답”이 아니라, **스펙으로 합의된 출력 규칙**입니다.

또 하나 중요한 말은,
실제 Flutter의 파이프라인과 “완전히 동일”하다고 주장하지 않습니다.

Flutter는 RenderObject 트리, relayout boundary 같은 디테일이 있고
여기 과제는 “출력 리스트 규칙”이 요구됩니다.

다만 공통점은,
**변경이 발생하면 상위로 영향이 전파되고, 그 과정이 테스트 가능한 규칙이어야 한다**는 사고방식입니다.

---

### 3.4 Cascading updates: fixed-point iteration + fail-safe (6:20–8:00)

네 번째는 연쇄 레이아웃 업데이트를 처리하는 방식입니다.

리프 노드의 변화가 부모의 크기를 바꾸고,
그게 다시 조부모의 크기를 바꾸는 경우가 있습니다.

그래서 저는 **fixed-point iteration**으로 처리했습니다.

핵심은 두 가지입니다.

1. **수렴 조건을 명시**합니다.
   - iteration 중에는 구조 변경을 하지 않는다
   - 레이아웃 계산은 자식 결과를 집계해서 부모가 결정되는 방향으로만 간다

2. 그리고 `maxIterations`는 “이론적 보장”이 아니라
   **운영 관점 fail-safe**입니다.

- 만약 반복 제한에 걸리면,
  “수렴 실패”로 보고 디버깅 가능한 정보를 남기고 빠져나옵니다.
  예를 들어 마지막 iteration에서 계속 갱신되는 노드 집합을 기록한다든지요.

이렇게 하면 “무한 루프”라는 최악의 운영 리스크를 제거하면서도,
정상 케이스에서는 충분히 수렴합니다.

---

### 3.5 paintOrder: preorder DFS는 “합의된 렌더 순서 리스트” (8:00–9:10)

다섯 번째는 `paintOrder`입니다.

저는 **preorder DFS**, 즉 **부모 → 자식** 순서를 사용했습니다.

여기서 중요한 전제는:
이 과제의 paintOrder는 실제 GPU 합성 모델을 완벽히 재현하는 게 아니라,
**예측 가능한 렌더 순서 리스트를 결정성 있게 출력**하는 목적입니다.

그래서 가장 직관적이고 일관된 규칙을 택했고,
특히 `Stack`처럼 겹침이 있는 경우에는 **children 순서를 그대로 유지**해서
“입력 순서가 곧 출력 순서”가 되게 했습니다.

---

## 4) 검증 전략 + AI 활용 방식 (9:10–10:40)

### 4.1 테스트 전략 (9:10–10:00)

저는 이 과제를 **테스트로 스펙을 잠그는 방식**으로 했습니다.

- 단위 테스트로 “이벤트별 전파 규칙”을 잠그고
- 통합 테스트로 “전체 파이프라인 결과”를 잠그고
- 회귀 테스트로 “결정성”을 확인했습니다.

특히 중요하게 본 케이스는:

- no-op이면 재계산 0
- 이벤트별 dirty 전파 규칙
- recomputeLayout 순서가 항상 동일
- cascading이 정상 수렴하거나 fail-safe가 동작하는지
- 동일 입력은 동일 출력

### 4.2 AI 활용 (10:00–10:40)

AI는 반복 코드와 boilerplate 생산에 활용했고,
**스펙·테스트·최종 리뷰는 제가 소유**했습니다.

프로세스는 간단히:

1. PLAN/DESIGN으로 제약을 고정
2. 테스트로 결과를 잠금
3. 구현 생성
4. diff 리뷰 + 엣지케이스 테스트 추가

그래서 “AI가 만든 코드”가 아니라,
**테스트로 검증된 설계가 남도록** 했습니다.

---

## 5) APR 직무 연결: BLE/운영/테스트 자동화로 “그대로” 옮길 수 있는 방식 (10:40–11:40)

APR의 AGE-R 앱은 BLE 디바이스 연동이 핵심이고,
운영 안정성과 테스트 자동화가 중요하다고 이해했습니다.

제가 이 과제에서 보여준 방식은 BLE에도 그대로 적용됩니다.

- BLE에서는 `Disconnected → Scanning → Connecting → Discovering → Ready → Syncing` 같은
  **상태머신을 명시**해야 하고
- notify / ack / timeout / retry는 **이벤트로 모델링**해서
  “규칙”이 되어야 테스트가 가능합니다.

이 과제의 dirty flags와 전파 규칙은,
BLE에서 “어떤 이벤트가 들어왔을 때 어떤 상태/부작용이 발생해야 하는지”를
**결정성 있게 정의하고 회귀로 잠그는 방식**과 같습니다.

그리고 Patrol 같은 E2E는
권한, 네이티브 다이얼로그, 웹뷰 브리징 같이
실제 운영에서 가장 많이 깨지는 구간을 회귀로 잠그는 데 기여할 수 있다고 봅니다.

정리하면, 이 프로젝트로 보여드린 핵심은 세 가지입니다.

1. 복잡한 규칙을 **스펙으로 고정**하는 능력

질문 주시면, 예를 들어

- BLE 연결 안정성을 규칙/테스트로 어떻게 잠글지

## (보너스) 면접관 질문 들어올 때 “짧게 치고 들어가는” 3개 답변

### Q1. “maxIterations=10 왜 10이에요?”

- “이건 이론적 보장 수치가 아니라 **fail-safe**입니다. 수렴 전제는 ‘구조 고정 + 단조 집계’고, 제한을 넘기면 수렴 실패로 보고 디버그 정보를 남기도록 설계했습니다.”

### Q2. “Flutter랑 같은 거 맞아요?”

- “완전히 같다고 말하진 않습니다. Flutter는 RenderObject/relayout boundary 등 디테일이 있고, 이 과제는 ‘출력 리스트 규칙’을 요구합니다. 다만 **변경 전파를 규칙으로 만들고 테스트로 잠그는 접근**은 실무에서도 동일하게 유효합니다.”

### Q3. “AI로 했다면 본인 실력은?”

- “스펙 고정과 검증은 제가 했고, AI는 반복 구현에만 썼습니다. 그래서 결과물은 ‘생성된 코드’가 아니라 **테스트로 검증된 규칙 집합**으로 남아 있습니다.”
