# APR 실무면접 — 예상 질문 & 답변 (최종 말하기 버전)

> **답변 원칙**: 2~3문장으로 핵심 → (있으면) 1줄 예시 → (마지막) APR 적용 한 문장

## A. 과제 관련 질문 (렌더 파이프라인)

### A-1. 왜 dirty를 2-tier로 나눴나? 1-tier면 뭐가 깨지나?

구조 변경과 레이아웃 변경은 **영향 범위와 출력 목적이 다르기** 때문에 `structureDirty`와 `layoutDirty`를 분리했습니다. 1-tier로 통합하면 `recomputeStructure`와 `recomputeLayout`을 출력에서 다시 역추론해야 해서 로직이 복잡해지고, 불필요한 구조 검증/재계산이 늘어납니다.

### A-2. recomputeLayout 순서 규칙을 왜 ‘타겟→부모→형제’로 고정했나? 반례는?

이 과제는 “계산 결과”뿐 아니라 **사람이 이해 가능한 출력 순서**가 스펙이기 때문에, 인과관계를 따라 타겟→부모→형제로 고정했습니다. 순서를 고정하지 않으면 디버깅 시 “왜 이 노드가 포함됐는지” 추적이 어려워지고, 자료구조 선택(Set 등)에 따라 결정성이 흔들릴 수 있습니다.

### A-3. fixed-point iteration이 수렴하지 않으면? maxIterations 근거는?

수렴의 전제는 **(1) iteration 중 구조 고정, (2) 자식 결과를 집계해서 부모가 결정되는 단방향 갱신**입니다. `maxIterations`는 이론적 보장치라기보다 **버그/예외 상황에서 무한 루프를 막는 fail-safe**이고, 초과 시 수렴 실패로 보고 디버깅 가능한 정보를 남기도록 설계하는 게 맞습니다.

### A-4. 결정성 보장은 어떤 레벨에서 확보했나?

결정성은 **순회 순서(자식은 List로 관리), 출력 규칙(타겟→부모→형제), 동등성 비교(no-op detection)** 세 레벨에서 확보했습니다. 즉 동일 입력이면 동일한 순회/동일한 수집/동일한 정렬 규칙을 타도록 만들어 테스트로 잠갔습니다.

### A-5. Flutter pipeline과 같고 다른 점은?

공통점은 **dirty 기반 증분 업데이트**라는 접근과, 변경이 전파되며 결과를 재계산한다는 큰 흐름입니다. 차이점은 Flutter는 Widget/Element/RenderObject 등 더 복잡한 계층과 constraint 전파/프레임 스케줄링 디테일이 있고, 이 과제는 **“출력 리스트의 규칙과 결정성”**을 요구하는 교육용 모델이라는 점입니다.

### A-6. Cascading update에서 무한 루프 가능성은?

구조를 고정하고 단방향(자식→부모 집계)으로만 갱신한다면 정상 케이스에서 반복은 결국 멈춥니다. 다만 구현 버그나 잘못된 갱신 규칙이 들어가면 무한 루프가 날 수 있으니, 운영 관점에서 `maxIterations`와 수렴 실패 시 진단 로그를 두는 게 안전합니다.

### A-7. setState는 왜 부모까지 dirty가 안 가나?

이 과제에서는 `setState`를 **크기/배치가 변하지 않는 상태 변경(리페인트 성격)**으로 정의했기 때문에 자기 노드만 영향을 받습니다. 크기/배치가 변하는 상태라면 스펙 상 `setSize` 같은 이벤트로 명시해서 레이아웃 영향 범위를 분리하는 게 일관됩니다.

### A-8. Row에서 자식 setSize 시 왜 형제도 dirty인가?

Row/Column은 자식의 크기가 바뀌면 **뒤에 있는 형제들의 좌표가 밀려서 재배치**가 필요합니다. 예를 들어 Row에서 A의 width가 커지면 B의 x 좌표가 바뀌기 때문에 B도 layout 재계산 대상이 됩니다.

### A-9. 테스트 217개는 어떤 기준으로 설계했나?

테스트는 **규칙 잠금(단위) → 파이프라인 잠금(통합) → 회귀/결정성 잠금(검증)**의 피라미드로 설계했습니다. 핵심은 “변경 없음이면 0 비용”, “이벤트별 전파 규칙”, “출력 순서 규칙”, “수렴/실패 안전장치”, “동일 입력 동일 출력”을 각각 독립적으로 깨기 어렵게 만든 겁니다.

### A-10. 확장한다면 무엇을 먼저 추가하나?

우선순위는 **(1) constraints 시스템**, **(2) paint 단계 분리/최적화**, **(3) 더 다양한 포지셔닝/겹침 규칙**입니다. 이유는 실제 UI는 레이아웃이 “합산”만으로 결정되지 않고, 제약 전달과 부분 리페인트가 성능/정확성을 좌우하기 때문입니다.

## B. 직무 관련 질문 (BLE/운영/테스트)

### B-1. BLE 연결이 자주 끊길 때 재연결/상태 동기화는?

저는 연결 흐름을 먼저 **상태머신으로 고정**하고(Disconnected→Scanning→Connecting→Ready), 각 상태에 타임아웃/재시도/백오프를 **규칙으로 명시**합니다. 그리고 재연결 직후에는 “전체 상태 pull→diff 반영” 같은 **동기화 단계를 분리**해 언제 붙어도 같은 결과가 나오게 합니다.

### B-2. 펌웨어 팀과 프로토콜 변경 충돌 시 릴리즈 전략은?

저는 **버전 협상 + 기능 게이팅(feature gate)**으로 호환 구간을 명확히 하고, 최신 기능이 안 돼도 핵심 플로우는 유지되게 설계합니다. 비슷하게 결제/정책 이슈에서도 외부 이해관계자와의 커뮤니케이션을 통해 운영 리스크를 줄이고, 필요하면 SDK/연동 레이어를 표준화하는 방식으로 해결해 온 경험이 있습니다.

### B-3. WebView/JS bridging 보안/안정성은?

JS 브리지는 외부 입력이라 보고 **허용 메시지 화이트리스트 + 스키마 검증**을 기본으로 두고, 결제/개인정보 같은 민감 기능은 네이티브에서만 처리합니다. 장애 대응은 경계면에서 타임아웃/예외를 잡아 관측에 태우며, 저는 Sentry+Crashlytics 통합 로깅 구조를 설계해 운영에서 재현/추적이 가능하게 만든 경험이 있습니다.

### B-4. E2E 테스트가 flaky할 때 우선순위/해결 방식은?

flaky는 원인을 **타이밍/격리/환경**으로 분류하고, 실패율이 높은 구간부터 테스트를 더 결정적으로 바꿉니다(명시적 wait, 상태 초기화, 환경 고정). 저는 관측 기반으로 재현성을 확보하는 편이고, 퍼널/리텐션 분석과 이벤트 로그 체계를 구축해 문제 구간을 좁혀온 경험이 있습니다.

### B-5. SonarQube에서 Critical 이슈가 뜨면?

Critical은 **머지 블로커**로 두고 즉시 수정합니다. 단순히 해당 라인만 고치는 게 아니라 “왜 발생했는지” 패턴을 찾아 테스트/룰로 재발 방지까지 묶는 방식으로 처리합니다.

### B-6. Patrol E2E를 도입하면 무엇부터 자동화하나?

가장 먼저 **핵심 사용자 여정**(로그인→권한→디바이스 스캔/연결→핵심 기능 실행)을 자동화합니다. 그 다음 Patrol 강점인 **권한/네이티브 다이얼로그/웹뷰 경계**를 회귀로 잠궈서, 운영에서 가장 자주 깨지는 구간의 리스크를 줄입니다.

### B-7. Flutter 배포 시 Android/iOS 각각 주의점은?

Android는 권한/백그라운드 제한, 릴리즈 난독화(R8)로 인한 리플렉션/직렬화 이슈, ABI/스토어 정책을 먼저 체크합니다. iOS는 Info.plist 권한 문구, 심사 정책(특히 결제/트래킹), 빌드 설정 차이로 인한 런타임 이슈를 사전에 점검합니다.

### B-8. 성능 최적화 경험과 지표는?

저는 체감 문제를 **지표로 바꿔** 프레임 드랍/콜드스타트/크래시율/전환율로 관리합니다. 실제로 Android SDK 대응 과정에서 크래시율을 70% 이상 낮춘 경험이 있고, 컴포넌트화로 개발 기간을 30% 이상 단축한 경험도 있습니다.

### B-9. AGE-R 앱에 새 기능 추가 시 진행 프로세스는?

저는 요구사항을 “실패/권한/오프라인/복구”까지 포함해 먼저 고정하고, 영향 범위를 문서화한 뒤 작은 PR 단위로 구현합니다. 테스트는 유닛/통합/E2E로 나눠 핵심 여정을 먼저 회귀로 잠그고, 배포 후에는 Crash/Analytics로 이상 징후를 모니터링합니다.

### B-10. 합류하면 가장 먼저 하고 싶은 일은?

첫 2주는 코드베이스와 핵심 플로우를 **직접 실행/추적**하면서, BLE/웹뷰/권한/테스트 구조를 빠르게 맵핑하겠습니다. 그 다음은 작은 버그 픽스나 테스트/관측 개선 같은 **작은 기여로 리듬을 맞추고**, 2~3개월 내 독립적으로 기능 단위를 책임질 상태를 목표로 합니다.

## C. 일반 질문 (태도/협업)

### C-1. 기술적 의견 충돌이 있을 때 어떻게 해결하나?

저는 의견 충돌을 “말싸움”이 아니라 **근거(정책/수치/실험)로 결정**하는 문제로 봅니다. 실제로 결제 정책 이슈에서 DevRel 커뮤니케이션을 주도해 방향을 정리했고, 필요하면 SDK/연동 레이어를 직접 표준화해 실행 가능한 결론으로 만든 경험이 있습니다.

### C-2. 모르는 기술을 빠르게 학습한 경험은?

저는 “작게 동작하는 프로토타입→실제 제품 적용→회귀/관측으로 잠금” 순서로 학습합니다. 예를 들어 결제 도메인에서 PortOne V2 연동이 필요해 패키지를 직접 만들고, 백엔드 웹훅/REST 동기화까지 붙여 운영 안정성을 확보했습니다.

### C-3. 강점과 약점은?

강점은 복잡한 문제를 구조로 푸는 능력이고, 실제로 Clean Architecture + Riverpod/Freezed/GoRouter로 유지보수 가능한 구조를 정립해 왔습니다.
약점은 완성도를 올리느라 초기 결정이 늦어질 수 있다는 점이라, 최근에는 “최소 동작 버전→측정→확장”으로 시간박스를 먼저 잡고 진행합니다.

### C-4. 마지막으로 하고 싶은 말은?

저는 기능을 빠르게 만드는 것에서 끝나지 않고 **운영 가능한 품질과 검증 체계**까지 책임지는 개발자라고 생각합니다. APR의 디바이스 연동/테스트 자동화/품질 지표 관리 같은 과제에, 제가 해온 “규칙 고정→테스트/관측으로 잠금→점진 개선” 방식으로 기여하겠습니다.

## 답변 시 유의사항 (최종)

### DO

- 2~3문장으로 끝내고, 파고들면 그때 예시 추가
- “원칙 → 사례(수치/근거) → APR 적용”으로 말하기
- 모르면 “모릅니다. 대신 이렇게 검증하겠습니다.”로 전환

### DON’T

- Flutter/BLE 등에서 **근거 없는 단정**(“원래 그렇다”) 금지
- 이력서에 없는 경험을 **있다고 말하지 않기**
- 설명을 1분 넘기기(질문 받으면 확장)
