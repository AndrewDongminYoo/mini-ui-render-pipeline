## A. 과제 관련 질문 (렌더 파이프라인)

### A-1. 왜 dirty를 2-tier로 나눴나? 1-tier면 뭐가 깨지나?

**답변**:

구조 변경(addChild)과 속성 변경(setSize)의 **영향 범위가 다르기 때문**입니다. 1-tier로 통합하면 setSize 이벤트에서도 구조 검증 과정을 거쳐야 하고, 출력 형식에서 `recomputeStructure`와 `recomputeLayout`을 정확히 구분할 수 없습니다.

**예시**: addChild는 트리 위상 자체를 바꾸므로 부모-자식 관계 재구축이 필요하지만, setSize는 크기만 바뀌므로 레이아웃 재계산만 필요합니다.

**반례**: 1-tier dirty flag 하나만 사용하면, "트리 구조는 안 바뀌었는데 크기만 바뀐" 경우를 구분할 수 없어서 불필요한 구조 검증이 매번 실행됩니다.

### A-2. recomputeLayout 순서 규칙을 왜 '타겟→부모→형제'로 고정했나? 반례는?

**답변**:

**인과관계의 흐름**을 따르기 때문입니다. 이벤트 타겟이 변경되면(원인) → 부모가 영향받고(1차 효과) → 형제가 재배치됩니다(2차 효과). 이 순서가 사용자가 "왜 이 노드가 재계산되나?"를 추적하기 가장 직관적입니다.

**반례**: 순서를 랜덤하게 하면 기술적으로는 문제없지만, ["B", "R", "A"] 같은 결과는 디버깅 시 혼란을 줍니다. 또한 Set을 사용하면 순서 비결정성이 생겨 동일 입력에도 다른 출력이 나올 수 있습니다.

**검증**: 테스트에서 217개 케이스 모두 정확한 순서를 assert로 검증했습니다.

### A-3. fixed-point iteration이 수렴하지 않으면? maxIterations는 근거가 있나?

**답변**:

**수렴 보장 조건**이 세 가지 있습니다:

1. **상향 전파만 허용** - 자식에서 부모로만 dirty 전파
2. **트리 구조 고정** - 이벤트 처리 중 노드 추가/삭제 없음
3. **유한한 트리 깊이** - 트리 깊이 N이면 최대 N번 iteration

**maxIterations = 10 근거**:

- 일반적인 UI 트리 깊이는 5~7 수준
- 여유를 두어 10으로 설정
- 10번 초과 시 무한 루프로 판단하고 에러 발생

**실제 테스트**: 4단계 중첩 구조에서 3번 iteration만에 수렴 확인했습니다.

### A-4. 결정성 보장은 어떤 레벨에서 확보했나? (순회 순서/정렬/동등성 비교)

**답변**:

**3가지 레벨에서 결정성을 확보**했습니다:

1. **순회 순서**: children을 List로 관리 (Set 아님), 항상 동일 순서 보장
2. **정렬**: recomputeLayout 리스트를 stable sort로 정렬 (타겟→부모→형제 규칙)
3. **동등성 비교**: no-op detection에서 `==` 연산자로 정확한 값 비교

**검증 방법**: 동일 JSON 입력을 100번 실행해도 출력이 완전히 동일함을 테스트로 확인했습니다.

**함정 피하기**: Dart의 `Set.toList()`는 순서 보장 안 함 → 사용 금지

### A-5. 이걸 실제 Flutter pipeline과 비교하면 뭐가 같고 뭐가 다른가?

**답변**:

**공통점**:

1. **Dirty Flag 패턴** - Flutter도 `markNeedsBuild()`, `markNeedsLayout()` 사용
2. **증분 업데이트** - 변경된 위젯만 재빌드
3. **Pre-order DFS** - Flutter도 부모 먼저 빌드

**차이점**:

1. **Constraints 전파** - Flutter는 "constraints down, size up" 규칙이지만, 이 프로젝트는 단순화된 레이아웃만
2. **스케줄링** - Flutter는 vsync 기반 프레임 스케줄링, 이 프로젝트는 이벤트 기반
3. **3-tree 구조** - Flutter는 Widget/Element/RenderObject 3단 구조, 이 프로젝트는 Node 1단 구조

**학습 목적**: Flutter의 핵심 원리는 동일하지만 복잡도를 낮춘 교육용 구현입니다.

### A-6. Cascading update에서 무한 루프 가능성은 없나?

**답변**:

**무한 루프는 불가능**합니다. 이유:

1. **방향성 그래프** - 트리 구조는 순환(cycle)이 없는 DAG
2. **단방향 전파** - 자식 → 부모로만 전파, 역방향 없음
3. **고정점 수렴** - 부모 크기가 확정되면 더 이상 변경 없음

**증명**: 트리 깊이가 N이면, 리프에서 시작한 dirty는 최대 N번 전파 후 루트에서 종료됩니다.

**방어 코드**: 그럼에도 maxIterations로 안전장치를 둬서, 혹시 모를 버그로 인한 무한 루프를 방지했습니다.

### A-7. setState 이벤트는 왜 본인만 dirty하고 부모는 영향 안 받나?

**답변**:

**커스텀 상태 변경**은 노드의 크기/위치에 영향을 주지 않는다고 가정하기 때문입니다. 예를 들어 버튼의 "isPressed" 상태 변경은 버튼 색상만 바꾸고, 크기는 그대로입니다.

**설계 의도**: setState는 "리페인트만 필요"한 변경을 나타냅니다. 만약 크기가 바뀌어야 한다면 setSize를 명시적으로 호출해야 합니다.

**확장 가능성**: 실제 Flutter에서는 `markNeedsPaint()`와 `markNeedsLayout()`이 분리돼 있듯, 이 프로젝트도 향후 "paintDirty" 플래그를 추가할 수 있습니다.

### A-8. Row의 자식이 setSize하면 왜 형제도 dirty되나?

**답변**:

**Row는 자식들을 가로로 배치**하므로, 한 자식의 너비가 바뀌면 **형제의 x 좌표가 이동**하기 때문입니다.

**예시**:

```plaintext
Row (너비 80)
├── A (50×20) → 60×20으로 변경
└── B (30×20)
```

A의 너비가 10 증가하면:

- A의 위치: (0, 0) → 그대로
- **B의 위치: (50, 0) → (60, 0)으로 이동** ← 형제 영향!
- Row 전체 너비: 80 → 90

따라서 B도 layoutDirty = true로 표시됩니다.

**Column도 마찬가지**: 자식 높이 변경 → 아래 형제의 y 좌표 이동

### A-10. 이 프로젝트를 확장한다면 어떤 기능을 추가하고 싶나?

**답변**:

**우선순위 순으로 3가지**:

1. **Constraints 시스템** (높음)
   - 현재: 부모가 자식 크기를 합산
   - 확장: 부모가 자식에게 제약 조건 전달 (min/max width)
   - Flutter의 BoxConstraints와 유사

2. **Paint 최적화** (중간)
   - 현재: 매번 전체 트리 pre-order DFS
   - 확장: paintDirty 플래그 추가, 변경된 subtree만 리페인트
   - Dirty region tracking

3. **Absolute/Relative Positioning** (낮음)
   - 현재: Row/Column의 자동 배치만
   - 확장: CSS의 position: absolute 같은 기능
   - 겹침(z-index) 관리

**근거**: APR의 AGE-R 앱처럼 복잡한 UI에서는 constraints와 paint 최적화가 핵심입니다.

## B. 직무 관련 질문 (BLE/운영/테스트)

### B-1. BLE 연결이 자주 끊기는 환경에서 재연결/상태 동기화는 어떻게 하나?

**답변**:

**3단계 재연결 전략**을 사용합니다:

**1. 상태 머신 모델링**

```diagram
Disconnected → Scanning → Connecting → Connected → Syncing → Ready
```

각 상태에서 재연결 로직이 명확히 정의됨

**2. 지수 백오프(Exponential Backoff) 재연결**

- 1차 시도: 즉시 재연결
- 2차 시도: 2초 후
- 3차 시도: 4초 후
- 최대 5회 시도 후 사용자에게 알림

**3. 상태 동기화 프로토콜**

- 연결 직후 디바이스에서 전체 상태 가져오기 (GET_STATE 커맨드)
- 앱 로컬 상태와 비교, 불일치 시 디바이스 우선
- 마지막 성공 시각 기록, 타임스탬프 기반 충돌 해결

**실전 경험**: IoT 프로젝트에서 GATT error 133 대응 경험 있습니다.

### B-2. 펌웨어 팀과 프로토콜 변경으로 충돌 났을 때 릴리즈 전략은?

**답변**:

**Versioning + Graceful Degradation** 전략을 사용합니다:

**1. 프로토콜 버전 협상**

- 연결 시 앱/펌웨어 버전 교환
- Characteristic에 version 필드 추가
- 예: 앱 v2.0, 펌웨어 v1.5 → 호환 가능한 기능만 활성화

**2. Feature Flag 활용**

```dart
if (deviceVersion >= 2.0) {
  // 새 기능 사용
  enableAdvancedFeature();
} else {
  // 레거시 프로토콜
  useLegacyProtocol();
}
```

**3. 단계적 배포**

- 펌웨어 OTA 먼저 배포 (backward compatible)
- 앱 업데이트는 1주일 후 배포
- A/B 테스트로 문제 감지

**협업 원칙**: 펌웨어 팀과 주간 동기화 미팅, API 스펙 문서 공유 (Notion/Swagger)

### B-3. WebView/JS bridging에서 보안/안정성은 어떻게 잡나?

**답변**:

**3가지 레이어로 방어**합니다:

**1. 화이트리스트 기반 메시지 검증**

```dart
// 허용된 메시지 타입만 처리
final allowedMessages = ['login', 'purchase', 'share'];
if (!allowedMessages.contains(message.type)) {
  return; // 차단
}
```

**2. 입력 검증 & 새니타이징**

- JS → Native로 오는 모든 데이터를 JSON 스키마로 검증
- XSS 방지: HTML escape, 스크립트 태그 제거
- 파라미터 타입 체크 (문자열, 숫자, 불린만 허용)

**3. 권한 요청 명시화**

- WebView에서 카메라/위치 접근 시 Native 다이얼로그로 사용자 확인
- 민감한 API (결제, 개인정보)는 Native에서만 처리

**안정성**:

- try-catch로 JS 에러 핸들링
- timeout 설정 (3초 내 응답 없으면 에러)
- Sentry에 WebView 에러 로깅

### B-4. E2E 테스트가 flaky할 때 우선순위/해결 방식은?

**답변**:

**Flaky 원인별 해결 전략**:

**1. Timing Issue (가장 흔함)**

- **원인**: 애니메이션/네트워크 딜레이
- **해결**: `pump()` 대신 `pumpAndSettle()`, explicit wait 사용

```dart
await tester.pumpAndSettle(Duration(seconds: 3));
await tester.waitFor(find.text('로그인 완료'));
```

**2. 테스트 격리 문제**

- **원인**: 이전 테스트의 상태가 남아있음
- **해결**: `setUp()`에서 완전 초기화, 공유 상태 제거

```dart
setUp(() async {
  await resetDatabase();
  await clearSharedPreferences();
});
```

**3. 환경 의존성**

- **원인**: 네트워크/시간대/로케일
- **해결**: Mock 사용, 환경 고정

```dart
mockNetworkImages(); // 네트워크 이미지 Mock
Clock.fixed(DateTime(2025, 1, 1)); // 시간 고정
```

**우선순위**: 실패율 > 영향 범위 > 수정 난이도 순으로 해결

**APR 문맥**: Patrol로 네이티브 다이얼로그/권한 요청도 테스트 가능하므로, 더 안정적인 E2E 구축 가능

### B-5. SonarQube 코드 품질 지표에서 "Critical" 이슈가 나오면 어떻게 대응하나?

**답변**:

**Critical 이슈는 무조건 수정 후 머지** 원칙입니다.

**대응 프로세스**:

**1. 즉시 분석**

- SonarQube 리포트 확인: 어떤 룰 위반인지, 위치는 어디인지
- 예: "Null pointer dereference", "SQL injection risk"

**2. 근본 원인 파악**

- 왜 이 이슈가 발생했나? (잘못된 null 체크, 입력 검증 누락)
- 다른 곳에도 동일 패턴 있나?

**3. 수정 + 회귀 방지**

- 해당 코드 수정
- 테스트 케이스 추가 (동일 이슈 재발 방지)
- Lint 규칙 강화 (가능하면)

**예시**:

```dart
// Before (Critical: Null 체크 누락)
final user = getUserById(id);
print(user.name); // NPE 위험!

// After
final user = getUserById(id);
if (user != null) {
  print(user.name);
}
```

**팀 문화**: Critical 이슈는 PR 블로커, Major는 일정 고려 후 수정

### B-6. Patrol E2E 테스트를 도입한다면 어떤 시나리오를 우선 자동화하나?

**답변**:

**APR AGE-R 앱 기준 우선순위**:

**1. Critical User Journey (최우선)**

- 로그인 → 디바이스 스캔 → 연결 → 디바이스 사용
- 이 플로우가 깨지면 앱 사용 불가

**2. 권한 요청 시나리오 (Patrol의 강점)**

- Bluetooth 권한 요청 → 허용/거부 테스트
- 위치 권한 (Android 12+ BLE 스캔 필수)
- 카메라 권한 (프로필 사진 변경)
- **Patrol은 네이티브 다이얼로그 조작 가능**

**3. BLE 연결 시나리오**

- 디바이스 스캔 → 목록 표시 → 선택 → 연결 → 연결 완료
- 연결 실패 시 재시도 플로우
- Mock BLE peripheral 사용

**4. WebView 통합 (포토그레이 기능)**

- WebView 로드 → JS bridging → Native 호출
- 딥링크 처리

**제외 시나리오**: 단순 UI 테스트 (위젯 테스트로 충분), 외부 API 의존 테스트 (Mock 권장)

### B-7. Flutter 앱 배포 시 Android/iOS 각각 주의할 점은?

**답변**:

**Android**:

**1. 권한 관리**

- Android 12+ BLE: `BLUETOOTH_SCAN`, `BLUETOOTH_CONNECT` 권한 필수
- 위치 권한: BLE 스캔 시 `ACCESS_FINE_LOCATION` 필요
- 런타임 권한 요청 로직 필수

**2. ProGuard/R8**

- Release 빌드 시 난독화로 리플렉션 깨질 수 있음
- `-keep class` 규칙 추가
- JSON 직렬화 클래스는 난독화 제외

**3. 64-bit 필수**

- Play Store 정책: arm64-v8a 필수
- `flutter build apk --split-per-abi` 권장

**iOS**:

**1. Info.plist 권한 설명**

- `NSBluetoothAlwaysUsageDescription`: "디바이스 연결을 위해 블루투스가 필요합니다"
- 설명이 부실하면 **리젝**

**2. Bitcode 비활성화**

- Flutter는 Bitcode 미지원
- Xcode 프로젝트 설정: `ENABLE_BITCODE = NO`

**3. App Tracking Transparency (ATT)**

- iOS 14.5+ 추적 권한 필수
- `NSUserTrackingUsageDescription` 추가

**공통**: Fastlane으로 배포 자동화, CI/CD에서 양쪽 빌드 동시 진행

---

### B-8. 앱 성능 최적화 경험이 있다면? 어떤 지표를 봤나?

**답변**:

**측정한 지표 3가지**:

**1. 프레임 드롭 (Jank)**

- **지표**: 60fps 기준, 16ms 초과 프레임 비율
- **도구**: Flutter DevTools Performance 탭
- **개선**: `ListView.builder` 사용, 무거운 연산 isolate로 분리

**2. 앱 시작 시간 (Cold Start)**

- **지표**: 앱 아이콘 탭 → 첫 화면 표시까지 시간
- **목표**: Android 3초 이내, iOS 2초 이내
- **개선**: 스플래시 화면에서 불필요한 초기화 제거, DI 최적화

**3. 메모리 사용량**

- **지표**: 메모리 peak, 메모리 누수
- **도구**: Xcode Instruments, Android Profiler
- **개선**: 이미지 캐싱 전략, 리스너 해제

**실전 사례**: 리스트 스크롤 시 프레임 드롭 40% → 5%로 개선 (이미지 로딩 최적화)
